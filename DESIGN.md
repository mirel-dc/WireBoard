# Wireboard — проект первой версии

Дата: 2026-10-06. Обновлено: 2026-10-08. Статус: первая версия реализована локально; проверка Windows/Linux и ограничения macOS описаны в README и work/verification.md.

## Назначение

Локальная доска для Windows, macOS и Linux, похожая по характеру взаимодействия на Wire из присланных скриншотов: пользователь и Codex могут создавать и редактировать одну и ту же схему. Это самостоятельная реализация по описанию, а не копия исходников Wire. По уточнению пользователя 2026-10-08 все три ОС входят в целевые платформы первой версии.

Из запроса следует: нужна собственная версия вместо недоступного форка, с интеграцией в Codex. После обсуждения пользователь выбрал Rust-бэкенд и браузерный frontend: Tauri не входит в первую версию. Предположения: интерфейс на русском; без аккаунтов, облачного хранения и собственного вызова AI API.

Основной сценарий: пользователь открывает доску, просит Codex добавить слайд или перестроить схему, видит изменения в открытом редакторе, корректирует их мышью и сохраняет результат. Codex использует установленную у пользователя модель и локальный CLI нашего приложения.

## Выбранный подход: Rust + браузер

Rust отвечает за модель доски, применение команд, сохранение, историю и API агента. Холст и панели — HTML/CSS/TypeScript и SVG в обычном браузере. React не требуется; Vite используется для разработки и сборки интерфейса. Node.js нужен при разработке, но не для запуска собранного приложения.

Один бинарник для выбранной ОС содержит сервер, встроенный frontend и команды CLI: `wireboard.exe` на Windows, `wireboard` на macOS и Linux. Команда `wireboard serve --open` (на Windows — `wireboard.exe serve --open`) запускает локальный сервер и открывает системный браузер. CLI-команды подключаются к запущенному серверу; логика транзакций и сохранения не дублируется в JavaScript. Для PNG используется Rust-рендеринг общего SVG через resvg с локально поставляемым шрифтом, без запуска Node.js или внешнего браузера.

На текущей машине 2026-10-06 проверены Rust/Cargo 1.96.0, toolchain `stable-x86_64-pc-windows-msvc` и Visual Studio 2022 Build Tools с компонентом VC Tools. Это проверка предварительных условий, а не подтверждение будущей сборки. Специальный WebView runtime приложению не нужен.

Общие Rust core, API, CLI и frontend используют одну кодовую базу. Платформенные различия изолируются в небольшом модуле: каталог данных, открытие браузера, файловая блокировка, атомарная замена файла и защита runtime-файла с токеном. Сборки выпускаются отдельно для ОС и архитектуры; целевые сочетания первой версии — Windows x86_64, macOS aarch64/x86_64 и Linux x86_64. Минимальные версии ОС и требования Linux к системным библиотекам фиксируются после выбора среды сборки и проверки готовых бинарников. Поддержка целевой платформы считается проверенной только после сборки и полного сценария запуска на ней.

Одна и та же доска переносится между ОС через экспорт/импорт JSON со встроенными изображениями; локальные пути не входят в документ доски. Каждая машина запускает собственный локальный сервер. Автоматическая синхронизация между машинами не входит в первую версию.

## Внешний вид

Тёплый светлый фон, ненавязчивая сетка точек, компактная панель инструментов, заметные линии и читаемые подписи. Акцент — приглушённый зелёный. Слева открываемая панель досок и слайдов; свойства выбранного объекта — справа. Основную площадь занимает холст.

Кнопки имеют подписи или доступные названия, видимый фокус и подсказки с горячими клавишами. Escape отменяет действие. Цвет дополняет форму или текст статуса. В режиме презентации скрываются сетка и панели.

Командные сочетания используют Ctrl на Windows/Linux и Cmd на macOS; подсказки показывают клавишу текущей платформы. Ввод текста сохраняет обычные сочетания браузера и ОС. При недоступности вставки изображения из буфера остаётся импорт через выбор файла.

Начальная демонстрационная доска показывает архитектуру самого Wireboard, чтобы сразу можно было проверить редактирование и управление агентом. Демонстрационные данные отделены от будущих пользовательских досок.

## Возможности первой версии

- Создание, переименование, открытие и удаление досок; удаление через подтверждение с названием доски.
- Прямоугольные блоки, текст, направленные связи и фреймы-слайды.
- Выделение одного и нескольких объектов, прямоугольник выделения, перетаскивание, изменение размера, дублирование, удаление, выравнивание и изменение цвета.
- Редактирование текста двойным щелчком; перенос строк внутри блока.
- Привязанные к блокам связи с подписью. При перемещении блока связь следует за ним; используется предсказуемая ортогональная трасса.
- Панорамирование, масштабирование около курсора, вписывание доски или выбранного слайда в окно.
- Фреймы 16:9 с именем; перемещение фрейма вместе с полностью содержащимися в нём объектами; порядок слайдов слева направо и сверху вниз.
- Режим презентации с переключением слайдов стрелками и выходом через Escape.
- Undo/Redo для изменений пользователя и агента, до 100 действий и не более 128 MiB истории в памяти приложения на доску. Самые старые действия удаляются при достижении любого лимита. История не сохраняется после перезапуска; это явно указано в документации.
- Автоматическое сохранение, отображение состояния сохранения, экспорт и импорт JSON, экспорт SVG и PNG доски или слайда.
- Вставка PNG/JPEG/WebP из файла или буфера обмена. SVG как входное изображение и загрузка изображений по URL откладываются; экспорт SVG поддерживается.
- Живое обновление открытого редактора после команд CLI через Server-Sent Events.

Первая версия не включает Tauri, облачную синхронизацию, совместную работу через интернет, импорт Miro, PDF, богатый текст или собственную AI-модель. MCP не требуется для первого рабочего сценария: CLI и skill дают Codex доступ ко всем нужным операциям; стандартный MCP можно добавить следующим этапом. Результат сборки для каждой целевой ОС и архитектуры — исполняемый файл, который обслуживает редактор и API и выполняет CLI-команды. Установщик не требуется для локального запуска.

## Компоненты

**Rust core** хранит модель доски и реализует валидацию, транзакции, геометрию, работу со связями и фреймами. Сериализация — serde. Он не зависит от DOM или HTTP и тестируется отдельно.

**Rust service/store** координирует изменение и сохранение досок, историю, версии и уведомления. Изменения пользователя и агента проходят через этот сервис с общей блокировкой состояния; порядок записи и уведомлений одинаков.

**HTTP-сервер** на Rust (axum/tokio) слушает только `127.0.0.1:9843`. Он отдаёт встроенный собранный frontend и API для браузера и CLI. После сохранения сервис отправляет событие обновления доски через SSE. Ошибка занятого порта завершает запуск с понятным сообщением; второй процесс не получает доступ к данным в обход первого. Ctrl+C корректно останавливает endpoint. Открытие и закрытие вкладки не управляет временем жизни сервера.

**SVG-редактор** показывает подтверждённое состояние доски, обрабатывает мышь и клавиатуру и отправляет законченные действия через HTTP API. Незаконченный ввод текста или перетаскивание не перезаписывается внешними изменениями: интерфейс сохраняет черновик и сообщает о конфликте. Координаты предпросмотра могут вычисляться frontend, но окончательная валидация и изменения всегда выполняются Rust core. Трассы связей, перенос строк и SVG экспорта рассчитываются Rust, чтобы результат CLI совпадал с редактором.

**Rust CLI** использует clap и обращается к HTTP API: `boards`, `create`, `inspect`, `apply`, `render`, `export`. Структурированные результаты и ошибки выводятся в JSON; при ошибке используется ненулевой код выхода. Операции передаются JSON-файлом или stdin, чтобы избежать проблем с кавычками в PowerShell. Если сервер выключен, CLI возвращает понятную ошибку, не изменяя файлы напрямую. Порт и каталог данных можно задать при запуске; runtime-файл позволяет CLI найти endpoint своего сервера.

**Экспорт** строит SVG в Rust из той же модели и трасс связей. resvg превращает его в PNG. Шрифт с поддержкой кириллицы и его лицензия включаются в проект; сетевые шрифты не нужны. Границы текста, перенос строк, размеры кадра и обрезка рассчитываются одинаково для холста и экспорта.

**Skill для Codex** объясняет путь к CLI, выбор нужной доски, проверку revision, пакетное изменение и проверку изображения после изменения. В процессе разработки skill хранится внутри проекта; установка в каталог skills пользователя — отдельное действие после проверки приложения.

## Данные и команды

Доска хранится в читаемом JSON: `version`, `id`, `title`, `revision`, `nextId`, `elements`. Объекты имеют стабильные числовые ID, тип, координаты, размеры и свойства. Связь хранит ID начального и конечного блока, порты и подпись. Камера и выделение сохраняются отдельно как состояние интерфейса.

Изображения хранятся как проверенные растровые данные; импорт и экспорт JSON остаётся переносимым. В первой версии используется встроенное base64: до 8 MiB исходных байтов на изображение и до 32 MiB JSON на доску. Поддерживаются только PNG/JPEG/WebP с проверкой MIME и сигнатуры. Максимум 2000 объектов на доску. Ограничения описываются в README и проверяются до изменения доски.

Пакет `apply` содержит `board`, ожидаемый `revision` и до 100 операций: create, update, move, resize, delete, duplicate, rename. Он проверяется целиком и применяется одним действием Undo. Некорректные числа, неизвестные поля, ссылки на отсутствующие объекты и неподдерживаемые типы отклоняются. Координаты ограничены диапазоном ±100000 px; размеры — от 20 до 10000 px; масштаб — от 10% до 400%. Максимальная длина текста одного объекта — 10000 символов.

Revision увеличивается после каждого подтверждённого изменения, включая Undo/Redo. Устаревшая revision возвращает конфликт; CLI не повторяет изменяющую команду автоматически. Агент повторно читает доску и решает, как продолжить.

Фреймы — геометрические контейнеры. При групповом перемещении набор переносимых объектов фиксируется в начале действия; каждый объект перемещается один раз, даже при совместном выделении фрейма и его содержимого. При удалении блока удаляются связанные с ним стрелки.

## Сохранение и ошибки

Корневой каталог данных по умолчанию: `%LOCALAPPDATA%\Wireboard` на Windows, `~/Library/Application Support/Wireboard` на macOS, `$XDG_DATA_HOME/wireboard` на Linux (при отсутствии или не абсолютном значении XDG_DATA_HOME — `~/.local/share/wireboard`). Доски хранятся в подкаталоге `boards`; `--data-dir` задаёт другой корневой каталог для сервера и CLI. Тестовый запуск использует явно отдельный каталог. Один процесс сервера владеет файловой блокировкой каталога. Пользовательские пути не принимаются как ID доски. Файл записывается во временный файл в том же каталоге и заменяет исходный после успешной записи; блокировка и атомарная замена проверяются на каждой целевой ОС. Успех операции и событие обновления отправляются после сохранения; ошибка записи не выдаётся за успех. Импорт в браузере использует выбор файла, экспорт — скачивание. CLI читает входные файлы и записывает экспорт в явно указанный локальный путь.

Ошибки чтения, повреждённые JSON, импорт неизвестной версии, конфликт revision и отказ сохранения показываются явно. Повреждённый файл не заменяется демонстрационной доской. При отказе команды интерфейс сохраняет текущий черновик до явного разрешения ситуации. При потере соединения статус сообщает о недоступности сохранения; незавершённое редактирование не считается сохранённым.

Валидация Host/Origin и Sec-Fetch-Site, отсутствие CORS и CSP защищают API от запросов с посторонних сайтов. Браузер открывает локальную библиотеку без входа и cookies; изменения требуют Origin редактора. CLI использует Bearer из приватного runtime-файла, явно неверный токен отклоняется и на чтении. Runtime содержит внутренний и опубликованный endpoint, чтобы Windows CLI мог найти Docker-сервер на нестандартном порту. API не исполняет произвольный JavaScript и не предоставляет произвольный доступ к файлам. Текст рисуется как текст, а не HTML.

Runtime-файл с токеном доступен только текущему пользователю: права 0600 на macOS/Linux и ограниченный ACL на Windows. Ошибка установки требуемых прав завершает запуск с явной ошибкой. Открытие браузера выполняется без конструирования shell-команды из пользовательского ввода; если системный браузер недоступен, сервер продолжает работу и печатает локальный URL без токена.

## Проверка готовности

1. На целевых ОС: `cargo test`, `cargo clippy` и сборка frontend; затем release-сборка Rust со встроенным frontend для соответствующей ОС и архитектуры. Запуск полученного бинарника без Vite, открытие редактора в системном браузере и завершение сервера с остановкой HTTP endpoint. Результаты записываются отдельно для каждого целевого сочетания; проверка на Windows не подтверждает запуск на macOS или Linux.
2. Создание схемы руками: два блока, стрелка, подпись, слайд; изменение размеров и текста; проверка выделения, перемещения, Undo/Redo.
3. Сохранение, перезапуск приложения и открытие той же доски с прежними объектами и изображением.
4. CLI создаёт второй слайд, добавляет объекты, связывает их и возвращает структуру. Открытый браузер показывает изменения без перезагрузки.
5. CLI получает PNG; SVG и PNG содержат весь выбранный слайд без панелей редактора и обрезают соседние объекты.
6. Тесты проверяют атомарность пакета, отказ при устаревшей revision, перенос фрейма без двойного перемещения, следование стрелок, ошибки записи и сохранение данных после перезапуска.
7. Проверка браузером через Playwright покрывает редактор, презентацию, импорт/экспорт, клавиатурные команды Ctrl/Cmd, SSE и внешний вид. Браузер подключается к реальному Rust-серверу, а не к mock API или только к Vite preview. Основной сценарий проверяется в Chromium, Firefox и WebKit; открытие браузера, буфер обмена и горячие клавиши дополнительно проверяются в системном браузере целевой ОС.
8. После написания кода проводится отдельное ревью Rust, TypeScript, общего API, файловых операций и пользовательского ввода. Итоговый отчёт различает успешную сборку, тесты модели и проверенный полный сценарий работающего сервера с браузером и CLI.
9. Экспорт доски с кириллицей и изображением на одной ОС импортируется на другой; содержимое сохраняется, новые изменения видны через CLI и браузер. Проверяются стандартный каталог данных, явный `--data-dir`, блокировка второго сервера, сохранение после перезапуска и права runtime-файла на каждой ОС.

## Visual C and comments (v2)

The implemented extension is specified in docs/superpowers/specs/2026-10-09-visual-c-comments-design.md. Comments live in the Board document with separate monotonic thread/message counters. Server-provided UTC timestamps and revision-checked apply keep replies and geometry changes atomic. Snapshots preserve orphan anchors, history restores the whole document, and all render paths exclude editor discussion. The strict legacy reader migrates v1 only in memory until the next successful write. CLI comments returns a consistent target/link/frame context for manual Codex or Claude work; neither agent resolves threads.

## Локальная библиотека — обновление 2026-10-10

Единица библиотеки — существующий StoredDocument в `boards/<id>.json` с доской, слайдами, комментариями, журналом и квитанциями. Отдельная СУБД для этого сценария не нужна. Библиотека видна слева, поддерживает поиск и открытие файла JSON. Адрес `/?board=<id>` однозначно открывает документ; корневой адрес показывает выбор доски, отсутствующий ID не заменяется случайной доской. Путь к хранилищу виден в библиотеке. Браузеры пользуются общими документами на сервере, локально сохраняя только настройки вида и идентификатор для собственного Undo.

Одноразовый обмен и cookies удалены. Браузерные чтения разрешены через обычный localhost/127.0.0.1; изменения требуют Origin редактора. Host, Origin, Sec-Fetch-Site, CSP и отсутствие CORS не дают чужой веб-странице доступ к API. CLI сохраняет Bearer из приватного runtime; явно неверный Bearer отклоняется даже на чтении для защиты от подключения к чужому серверу после переиспользования порта. Docker публикует только loopback-порт. Это локальное приложение, без пользователей и облачной синхронизации.

Compose монтирует обычный каталог компьютера. `just` вычисляет native-путь по ОС и использует UID/GID пользователя на Unix; прямому Compose нужен явный WIREBOARD_DATA_DIR. Переход с старого тома выполняется с резервной копией и сверкой содержимого до переключения. Одновременные серверы для одного каталога запрещены; Docker/native являются альтернативами.

### Постоянные читаемые ссылки (2026-10-11)

`/b/<slug>` открывает редактор и выбирает доску по `slug` из списка библиотеки. Legacy `?board=<uuid>` канонизируется в slug без нового шага history. `links.json` в корне библиотеки хранит version 1 и отображение UUID → slug; документы досок не переписываются. Резервация ссылки атомарно сохраняется перед первым сохранением новой или импортированной доски. При сбое сохранения доски может остаться зарезервированное имя; существующая доска без долговечной ссылки не создаётся. Переименование не меняет slug, удаление не освобождает его для другой доски. Идентификаторы API/CLI и структура файлов остаются прежними. Повреждённый индекс блокирует запуск вместо переназначения ссылок.
