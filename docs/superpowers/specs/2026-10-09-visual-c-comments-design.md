# Wireboard: визуальный стиль C и комментарии для агента

Дата: 2026-10-09. Статус: готово к проверке пользователем. Это дизайн-спецификация следующего изменения, а не отчёт о реализованных возможностях.

## 1. Цель и принятые решения

Сделать существующий редактор Wireboard визуально проще и понятнее. Пользователь оставляет замечание прямо у объекта схемы, затем просит Codex или Claude обработать открытые комментарии. Агент читает контекст, меняет схему и отвечает в той же ветке. Пользователь проверяет результат.

Подтверждено в разговоре:

- Выбран вариант **C — цветные карточки**: светлый холст, сиреневый акцент, крупные заголовки, цвет по смыслу блока, компактные контекстные инструменты.
- Комментарии могут относиться к блоку, связи или месту на холсте.
- Запуск агента происходит **по команде пользователя**: «разбери открытые комментарии». Автоматический запуск при добавлении комментария не требуется.
- Пользователь поручил составить эту спеку по Superpowers. Реализация начнётся после проверки письменной спеки и отдельного плана реализации.

Решения, конкретизированные в этой спеке: три статуса ветки; сохранение обсуждения после удаления объекта; отдельный заголовок карточки; обратная совместимость через формат доски v2; ответы агента и изменения схемы в одной транзакции. Эти решения входят в предмет проверки документа.

Успех: обычная схема читается без настройки каждого блока вручную; замечание не теряет контекст; агент получает структурированные данные; результат можно проверить в браузере; сохранность старых досок подтверждена тестами.

## 3. Дизайн редактора

### 3.1. Композиция

- Верхняя строка: название доски, компактный статус сохранения, презентация, экспорт, кнопка комментариев с числом нерешённых веток. Высота 60–64 px.
- Панель досок и слайдов по умолчанию свёрнута. Кнопка «Доски и слайды» открывает её слева. Состояние сохраняется для текущего браузера. Вместо декоративных надписей используются обычные названия разделов.
- Слайды показываются миниатюрой и названием. Миниатюра использует тот же SVG-рендерер; обновляется по подтверждённому состоянию доски, не на каждом движении мыши.
- Панель основных инструментов плавает сверху холста. Все иконки — единый локальный SVG-набор с одинаковой толщиной линии; emoji и разнородные символы заменяются.
- При выделении объекта снизу появляется компактная панель: текст, размер шрифта/пресет, цвета, комментарий, дополнительные действия. Точные размеры, выравнивание, дублирование и удаление доступны через раскрываемые свойства. Без выделения панель скрыта.
- Комментарии открываются справа шириной 320–360 px. На широком экране панель занимает собственное место, а холст сжимается. Она не перекрывает выбранный объект; камера может панорамировать к нему без изменения масштаба.
- Для окна уже 900 px боковые панели становятся поочерёдными выдвижными панелями. На 375 px инструментальная строка допускает горизонтальную прокрутку. Комментарии и свойства остаются доступны, даже если постоянная колонка не помещается.
- Масштаб остаётся внизу. Постоянные подсказки сокращаются до одной строки и не закрывают органы управления.

### 3.2. Палитра и форма

Холст почти белый с лёгким сиреневым оттенком; панели белые; основной текст графитовый. Акцент сиреневый применяется к активному инструменту, выбранному объекту и действиям. Сетка мелкая и слабая, без конкуренции с содержимым.

Ориентиры CSS: холст `oklch(98% .01 300)`, текст `oklch(28% .034 295)`, акцент `oklch(52% .15 295)`. Точные токены корректируются только для соблюдения контраста; визуальное направление сохраняется.

Пресеты карточек сохраняются обычными существующими `fill`/`stroke` в формате `#RRGGBB`:

| Пресет | Заливка | Рамка | Пример использования |
| --- | --- | --- | --- |
| Нейтральный, по умолчанию | `#ffffff` | `#ddd7e5` | Обычный блок |
| Тёплый | `#fff0cf` | `#e5cd94` | Человек, исходная идея |
| Мятный | `#ddf5e9` | `#a9d6bf` | Общая доска, данные |
| Сиреневый | `#eee4ff` | `#cbb8e6` | Агент, обработка |

Цвет выбирает пользователь; приложение не угадывает роль объекта по названию. Подписи пресетов описывают цвет. Произвольный цвет по-прежнему доступен. Пользовательские заливки и рамки существующих объектов сохраняются.

Прямоугольная карточка: скругление 20 единиц холста, рамка 1–1.5, внутренний отступ 20. Новая карточка 240×160. Слайды сохраняют 16:9, получают скругление 12 и тонкую рамку. Дополнительные тяжёлые тени у каждой карточки не нужны.

Связь тонкая, с компактным наконечником; ортогональная трассировка и выбор портов сохраняются. Подписи связей имеют небольшой фон и отступ. `fill`/`stroke` продолжают действовать и в экспорте.

### 3.3. Типографика и текст

Остаётся поставляемый Golos Text. Заголовок карточки и описание — разные поля:

- `title`: заголовок только прямоугольной карточки, до 256 символов; допускает перенос слов, не более двух видимых строк.
- `text`: существующий основной текст, до 10000 символов, сохраняет своё значение и смысл.
- `fontSize`: размер основного текста; новый блок получает 16. Заголовок — `min(fontSize + 8, 96)`, начертание 600. Между заголовком и описанием 8 единиц; межстрочное расстояние 1.35.
- `fontWeight`: новое поле основного текста, 400 или 600, по умолчанию 400. Для текстового объекта пресеты «Заголовок», «Текст», «Подпись» задают соответственно 32/600, 16/400, 12/400. Пресеты — готовые настройки, не новая система богатого текста.

Для `text`, `connector`, `frame`, `image` поле `title` пустое; заголовок слайда и подпись связи остаются в `text`. `fontWeight` влияет на существующий основной текст; фиксированный размер подписи связи сохраняется в этой версии. Текстовые поля передаются и рисуются как обычный текст.

Двойной щелчок или Enter начинает редактирование непосредственно рядом с объектом: для карточки два поля «Название» и «Описание», для текста/связи/слайда одно поле. Используется HTML-оверлей редактора над SVG, без HTML в сохраняемой модели. Изменения применяются одной транзакцией по «Сохранить» или Ctrl/Cmd+Enter; Escape отменяет. Enter внутри многострочного поля вставляет новую строку. Клик за пределами редактора не сохраняет и не удаляет черновик.

При внешнем изменении доски черновик остаётся. Пользователь видит конфликт и явно выбирает повторное применение или отмену. Нужна прежняя проверка `revision`.

Полный текст не обрезается в данных. Если текст не помещается, видимый конец отмечается многоточием, а в редакторе появляется действие «Подогнать высоту под текст». Автоматический рост при наборе не перемещает соседние объекты. Подгонка высоты — отдельное сохраняемое действие; только для карточки или текстового объекта. У слайда сохраняется 16:9.

Измерение, перенос строк и выделение места под заголовок выполняются общим Rust-рендерером, с учётом размера и веса шрифта. SVG, PNG и браузер должны показывать одинаковую иерархию и переносы. В обоих путях доступны реальные начертания 400 и 600; визуальная проверка PNG обязательна, наличие атрибута `font-weight` само по себе не подтверждает результат.

## 4. Комментарии в интерфейсе

В инструментальной панели появляется «Комментарий» с клавишей C. Клавиша действует только вне полей ввода. Пользователь кликает объект или точку холста, набирает сообщение и нажимает «Добавить». До подтверждённого сохранения метка считается черновиком. Escape отменяет размещение.

Для уже выделенного объекта действие «Комментировать» находится в контекстной панели. Для работы с клавиатуры это основной путь, не требующий точного попадания в холст.

У ветки — стабильная номерная метка. Она не становится объектом схемы: не участвует в общем выделении, выравнивании, дублировании и геометрии связей. Размер метки 28 px на экране, область нажатия не меньше 44 px, независимо от zoom. При совпадении меток приложение разводит их на экране, не меняя сохранённую привязку, и показывает тонкую линию к якорю.

Нажатие метки открывает ветку справа. «Показать на схеме» перемещает камеру к привязке. В списке видны объект, статус, автор, время и сообщения. Автор отображается как «Ты», «Codex» или «Claude»; статусы различаются и цветом, и текстом.

Фильтры: «Открытые», «На проверке», «Решённые», «Все». По умолчанию видны открытые и ожидающие проверки ветки; фильтры можно включать совместно. Решённые метки скрыты до включения соответствующего фильтра. При открытии ветки из списка её метка становится видна независимо от текущего фильтра.

В выбранной ветке есть поле ответа. Смена ветки, закрытие панели и переход к другой доске не уничтожают незавершённый ответ: черновик сохраняется в памяти вкладки по ID доски и ветки. При наличии черновиков закрытие вкладки требует обычного предупреждения браузера. Черновики не выдаются за сохранённые сообщения и не обещают сохранность после перезапуска браузера.

Комментарии доступны в редакторе. Презентация, SVG/PNG и PNG миниатюр не содержат меток, панелей и сообщений. JSON переносит обсуждение полностью.

## 5. Жизненный цикл ветки

| Состояние API | Интерфейс | Смысл |
| --- | --- | --- |
| `open` | Открыт | Новый запрос, вопрос или замечание, ожидающее обработки |
| `awaiting_review` | На проверке | Агент дал итоговый ответ; изменения или объяснение ожидают пользователя |
| `resolved` | Решён | Пользователь закрыл обсуждение |

Правила переходов:

1. Новая ветка всегда `open`.
2. Ответ агента с `submitForReview: true` переводит открытую ветку в `awaiting_review`. Ответ содержит конкретное описание результата. Допустим результат без изменений схемы, если запрос был вопросом.
3. Уточняющий ответ агента с `submitForReview: false` оставляет `open`. Если агент обнаружил проблему в собственном результате на проверке, такой ответ возвращает `awaiting_review` в `open`; проблема не изображается как выполненная правка. Повторный итоговый ответ с `true` снова передаёт результат на проверку.
4. Кнопка «Принять» переводит `awaiting_review` в `resolved`. Пользователь может также закрыть `open`, если вопрос потерял актуальность.
5. Новый ответ пользователя в `awaiting_review` или `resolved` возвращает ветку в `open`. «Открыть снова» делает то же без нового сообщения.
6. Агент не закрывает ветку и не отвечает в уже решённую. В своей текущей работе он может дополнять результат в `awaiting_review`, пока пользователь его не принял; новый запуск по умолчанию такие ветки не обрабатывает. Если ветка была закрыта во время работы, агент перечитывает её и прекращает применение прежнего запроса.
7. Другие изменения схемы сами по себе не меняют статус. Принятие выполняется по текущей версии доски: пользователь проверяет актуальное состояние, не исторический снимок.

Отдельный статус «В работе», назначение исполнителя и блокировки веток не вводятся. Одновременные агенты защищены общей проверкой версии; второй обязан перечитать результат первого. Автоматического исполнения из текста комментария нет.

## 6. Модель данных и привязки

### 6.1. Формат доски v2

К существующей модели добавляются `comments: CommentThread[]`, `nextCommentId` и `nextMessageId`. `nextId` продолжает относиться только к объектам схемы. Все счётчики положительные целые, не больше `MAX_SAFE_ID`; ID не повторяются в соответствующей области и меньше следующего счётчика. Номера сообщений уникальны в пределах доски, а не только одной ветки.

`CommentThread`:

| Поле | Назначение |
| --- | --- |
| `id` | Стабильный номер ветки и метки |
| `anchor` | Типизированная привязка |
| `anchorSnapshot` | Последние известные сведения об объекте и точке; `null` для свободной точки |
| `status` | Одно из трёх состояний |
| `messages` | Непустой упорядоченный массив сообщений |
| `createdAt`, `updatedAt` | UTC RFC3339; время назначает сервер |
| `reviewRevision` | Версия доски, в которой агент передал результат на проверку; иначе `null` |

`CommentMessage`: `id`, `author` (`user`, `codex`, `claude`), `text`, `createdAt`. Изменение и удаление опубликованных сообщений не входят в эту версию. Ошибку можно исправить следующим ответом. История восстанавливается Undo/Redo как часть состояния доски.

Каноническая валидация v2 проверяет типы и диапазоны якоря, непустую ветку, уникальность ID и возрастание ID сообщений; даты должны разбираться как UTC RFC3339. `updatedAt` не раньше `createdAt`. В `open` поле `reviewRevision` равно `null`; в `awaiting_review` оно обязательно, находится в `[0, revision]`; в `resolved` допустимо `null` для закрытого без обработки вопроса либо число из того же диапазона. Неизвестные поля, типы и состояния отклоняются, как в текущей модели.

Автор — метка локального действия, не удостоверенная личность и не отдельный облачный аккаунт. HTTP-авторизация остаётся общей локальной. Проверки переходов по `author` защищают от ошибочного использования протокола; это не отдельная граница доступа между людьми.

Лимиты: 500 веток на доску, 100 сообщений в ветке, 10000 сообщений суммарно, 4000 символов в одном сообщении. Пустой после обрезки пробелов текст отклоняется; исходный текст сохраняется без изменения внутренних пробелов и переносов. Общий JSON по-прежнему не более 32 MiB, пакет до 100 операций, объекты до 2000. Обсуждение не увеличивает число объектов схемы.

### 6.2. Привязка к объекту или точке

- Объект: `{ type: "element", elementId, u, v }`, где `u` и `v` в `[0,1]` — нормализованная точка в прямоугольнике блока, текста, изображения или слайда. При добавлении через контекстное действие используется правый верхний угол (`1,0`).
- Связь: `{ type: "connector", elementId, t }`, где `t` в `[0,1]` — доля длины текущей ломаной связи. Контекстное действие выбирает `0.5`. Привязка пересчитывается после изменения трассы, а не хранит старую экранную позицию.
- Свободная точка: `{ type: "point", x, y }` в координатах доски; диапазон ±100000. Масштаб и панорамирование не меняют её координаты. При перемещении слайда свободная точка не переносится; комментарий, который должен следовать за слайдом, привязывается к самому слайду.

Сервер проверяет существование и подходящий тип объекта при создании/перепривязке. Перемещение и размер объекта изменяют положение его метки; при перемещении слайда метки внутренних объектов следуют за своими объектами. Во время перетаскивания они следуют за preview, после отказа транзакции возвращаются.

Для объекта `anchorSnapshot` содержит `elementId`, `kind`, `title`, `text`, `x`, `y`, `width`, `height`, `worldX`, `worldY`. Связь дополнительно сохраняет `from` и `to`. Снимок обновляется по подтверждённой геометрии и тексту; служебное обновление не меняет `updatedAt` ветки и её статус.

При удалении объекта или связи ветка остаётся с прежним якорем и последним снимком. `orphaned` вычисляется при чтении по отсутствию объекта; это не четвёртый статус. Метка остаётся у последней точки, список показывает «Объект удалён». Undo удаления восстанавливает обычную привязку. Агент видит `target: null`, снимок и явный признак; не создаёт замену по догадке. Пользователь может перепривязать ветку или закрыть её.

Импорт разрешает такой отсутствующий якорь только при наличии корректного снимка с тем же `elementId` и подходящим типом. Нельзя создавать новую ветку на несуществующем объекте через обычную операцию. Дублирование объекта/слайда не копирует обсуждение. История относится к исходному объекту.

## 7. Транзакции, API и CLI

### 7.1. Единственный путь записи

Добавления/ответы/статусы проходят через существующий `POST /api/boards/{id}/apply` с `revision` и массивом операций. Отдельного хранилища обсуждений и прямой записи JSON из CLI нет.

Новые операции:

| Операция | Параметры | Поведение |
| --- | --- | --- |
| `comment_create` | `anchor`, `author`, `text` | Выделяет ID ветки и первого сообщения; `open` |
| `comment_reply` | `threadId`, `author`, `text`, `submitForReview` | Добавляет сообщение и применяет правила статуса |
| `comment_status` | `threadId`, `author: "user"`, `status: "open"` или `"resolved"` | Закрывает или открывает обсуждение |
| `comment_reanchor` | `threadId`, `author: "user"`, `anchor` | Меняет привязку и снимок; возвращает ветку в `open` |

`comment_create` допускает все три метки автора. `comment_reply` требует явный boolean `submitForReview`; для `user` допускается только `false`. Агент отвечает в `open` или `awaiting_review`, но не в `resolved`. `comment_status` и `comment_reanchor` с агентской меткой отклоняются. Новая ветка используется в последующих запросах после получения выделенного ID; ссылки на ещё не созданную ветку в том же пакете не поддерживаются.

Полное подтверждённое состояние возвращается после успеха. Весь пакет сохраняется атомарно и составляет одно Undo. Обновление карточек, итоговый ответ и перевод на проверку должны идти в одном пакете. Если большая правка требует более 100 операций, агент делит её на осмысленные пакеты, а результат на проверку отправляет только после последнего успешного пакета; при частичном выполнении честно описывает его в открытой ветке.

`reviewRevision` устанавливается в итоговую `revision` транзакции с `submitForReview: true`. При возврате в `open` очищается; в `resolved` сохраняется для объяснения результата. Одновременный ответ пользователя приводит к конфликту старого пакета агента.

UTC-время операции задаёт store на один пакет и передаёт в чистую модель как контекст транзакции. Core не обращается к сети, DOM или часам сам. После успешной записи — существующее SSE-событие `board` с новой `revision`. Правки обсуждения используют ту же систему событий.

Undo/Redo восстанавливает и схему, и сообщения/статусы соответствующей транзакции. `revision` растёт, а `nextId`, `nextCommentId`, `nextMessageId` берутся не ниже текущих счётчиков: старые номера не переиспользуются. Лимит истории 100 действий/128 MiB учитывает комментарии. После перезапуска история Undo отсутствует, но обсуждение сохраняется.

### 7.2. Чтение для агента

`inspect` возвращает всю каноническую доску v2 вместе с обсуждением. Добавляется read-only endpoint `GET /api/boards/{id}/comments?status=open` и CLI:

```text
wireboard comments BOARD_ID --status open
wireboard comments BOARD_ID --status awaiting_review
wireboard comments BOARD_ID --status all --thread 1
```

`--status` по умолчанию `open`; допустимы `open`, `awaiting_review`, `resolved`, `all`. `--thread` необязательный фильтр; существующая ветка, исключённая статусом, даёт пустой список. Несуществующий номер даёт `missing`.

Ответ: `boardId`, `title`, `revision`, `threads`. Каждая ветка содержит её сообщения, статус, якорь, снимок, `orphaned`, текущий `target` или `null`, связанные входящие/исходящие стрелки и окружающий слайд. Если объект находится в нескольких слайдах, выбирается наименьший по площади, при равенстве — с меньшим ID. Для связи контекст включает оба конца. Для свободной точки возвращаются ближайший содержащий слайд по тому же правилу и координаты. Сортировка веток по ID, сообщений — по ID.

Чтение берёт единый снимок под store-блокировкой, чтобы контекст и `revision` совпадали. Агент дополнительно вызывает `inspect`, если нуждается во всей схеме. В случае изменения версии между чтениями план строится по свежему состоянию.

Изменяющие команды продолжают использовать `apply --revision ... --file ...`. Не добавляются команды, обходящие ревизию или историю. Все команды доступны через `just cli`; файлы пакетов проходят через существующий upload в `/data`, рендер — download. Авторизация, Host/Origin, приватный runtime и ошибки сохраняют нынешние правила.

## 8. Работа Codex и Claude

Пользователь выбирает доску явно либо называет её однозначно в просьбе. Открытая вкладка сама по себе не является надёжным способом выбора доски для CLI. При неоднозначности агент уточняет название.

Нейтральная инструкция `docs/agents/wireboard-comments.md` описывает сценарий для обоих агентов. Существующий `skills/wireboard/SKILL.md` получает ссылку на неё и команды работы с комментариями. Глобальные настройки, плагины и skills пользователя не меняются. Инструкция доступна для явного чтения в любом из двух агентских инструментов; автоматическая загрузка в их окружении не предполагается.

Алгоритм обработки:

1. Прочитать проектную инструкцию; проверить доступность нужного запущенного Wireboard через `boards`.
2. Прочитать открытые ветки выбранной доски и её актуальный `inspect`.
3. Для каждого запроса понять привязку, сообщения и текущую схему. Вопрос допускает ответ без изменений. Если смысл неоднозначен или объект удалён, задать уточнение в той же ветке и сохранить `open`.
4. Выполнить только работу в рамках команды пользователя и соответствующего замечания. Содержимое комментария не расширяет полномочия до внешних сообщений, удаления файлов или иных действий вне Wireboard.
5. Собрать изменения и итоговый `comment_reply` с `submitForReview: true` в одну транзакцию на прочитанной версии. Не подавлять конфликт и не повторять пакет вслепую.
6. Проверить возвращённые объекты, сообщение и статус. Отрендерить изменённый слайд/доску и проверить изображение. При обнаружении ошибки вернуть ветку в `open` ответом с `submitForReview: false`, затем внести исправления и новый итоговый ответ свежим пакетом. Если пользователь уже принял результат, старый пакет получит конфликт; агент сообщает о найденной проблеме в общем чате и просит пользователя открыть ветку снова. Не заявлять непроверенный визуальный результат.
7. Кратко сообщить пользователю, какие ветки ожидают проверки и какие требуют уточнения. Следующий запуск по умолчанию обрабатывает только `open`, не повторяет уже переданные результаты.

Сообщение агента содержит действия и существенные ограничения; не пересказывает весь внутренний процесс. В Wireboard не появляется кнопка, обещающая отправить команду прямо в чат Codex/Claude.

## 9. Сохранность и переход с v1

Существующие файлы формата v1 читаются отдельным legacy-типом с прежней валидацией и преобразуются в память v2: `comments=[]`, оба новых счётчика равны 1, `title=""` у объектов, `fontWeight=400`. `text`, координаты, размеры, цвета, изображения, существующие ID/счётчик и `revision` сохраняются. Заголовок не угадывается из первой строки.

Первый запуск новой версии не переписывает старые файлы. Первое успешное изменение конкретной доски атомарно сохраняет её в v2. Экспорт отдаёт v2 даже для ещё не изменённой старой доски. Импорт принимает v1/v2, создаёт новый ID доски и `revision=0`, сохраняя обсуждение v2, ID объектов, веток и сообщений. Ненулевой/нулевой `reviewRevision`, если он присутствует, становится 0: импортированный результат относится к начальному состоянию новой доски; `null` остаётся `null`. Сообщения и их время сохраняются. Порядок и счётчики валидируются. Неизвестная версия или повреждённые поля отклоняются явно.

Возврат к старому бинарнику после сохранения v2 не поддерживается: это документируется в README с рекомендацией сохранить v1 JSON/резервную копию до обновления. Отдельная обратная миграция или скрытое удаление комментариев не выполняются.

Старая доска получает новый chrome редактора и форму карточек, но её содержимое и пользовательские настройки не заменяются демонстрационными. Новые карточки получают новые значения по умолчанию. Пользователь может явно добавить заголовок старому блоку; это обычная сохраняемая правка.

## 10. Ошибки и доступность

- Потеря соединения/ошибка записи: сообщение остаётся черновиком, не появляется ложный статус успеха. Конфликт версии требует перечитать доску и явного решения о повторе. Если первоначальная запись имеет неопределённый результат, сохраняется нынешняя блокировка store до перезапуска.
- Нельзя автоматически повторять отправку комментария после timeout: ответ мог потеряться после сохранения. Клиент перечитывает ветку; пользователь подтверждает повтор, если не может установить результат.
- Превышение лимита показывает конкретное ограничение. Никакое обсуждение не удаляется для освобождения места автоматически.
- Внешнее SSE-обновление не уничтожает редактируемый текст объекта или ответа. После отмены черновика показывается актуальная версия.
- Фокус виден у каждой кнопки и поля; иконки имеют доступные названия. Нажатие метки открывает ветку с фокусом на заголовке/ответе; закрытие возвращает фокус к инициатору. Escape сначала закрывает вложенное меню/редактор, затем боковую панель.
- Все действия с комментариями доступны через панель списка; цвет дополняет номер и текст состояния. Контраст обычного текста не ниже 4.5:1, элементов управления/фокуса — 3:1. Минимальная область нажатия 44×44 px.
- Сообщения и заголовки выводятся безопасным текстом, с экранированием в SVG. Нет интерпретации HTML, JS или команд shell. Вывод CLI — JSON, не текст для исполнения.

## 12. Проверка готовности

Тесты модели/store/API:

1. Загрузка v1 без переписывания файла; изменение и экспорт v2; импорт v1/v2; отказ повреждённого формата и неизвестной версии; сохранность кириллицы, текста, цветов и изображения.
2. Все разрешённые/запрещённые переходы статуса; роли автора; ответы пользователя открывают ветку; агент не закрывает её.
3. Перемещение/resize объекта и слайда, новая трасса связи, удаление/Undo, перепривязка; свободная точка не меняется при pan/zoom; дублирование не копирует ветки.
4. Ошибка одной операции отменяет схему, сообщение и статус всего пакета. Ошибка persistence не выдаёт успех/SSE. Устаревшая `revision` не добавляет ответ и не перезаписывает замечание пользователя.
5. Undo/Redo восстанавливает весь пакет и не переиспользует три типа ID. Перезапуск сохраняет обсуждение; новый запуск не обещает сохранность Undo.
6. Лимиты сообщений/веток/JSON, пустые и опасные строковые значения, отсутствующие якоря, несовпадение снимка, ограничения счётчиков.
7. Чтение `comments` возвращает согласованный контекст, фильтры и ошибку отсутствующей ветки; `inspect` включает всё обсуждение.
8. Заголовок/описание, реальный вес шрифта, перенос кириллицы, многоточие и подгонка размера; SVG и PNG сопоставляются визуально. Презентация/экспорт не содержат комментариев, JSON содержит.

Браузерный сценарий с реальным Rust-сервером:

- Создать три карточки с заголовками и описаниями, соединить, добавить слайд. Проверить C layout, inline editing, клавиатуру, изменение цвета и Undo.
- Добавить ветки на блок, связь и точку; переместить и удалить объект; проверить метки, фильтры, перепривязку и черновики.
- Второй клиент/CLI меняет схему и отправляет ответ атомарно. Первый браузер получает SSE и «На проверке» без reload. Ответ агента и изменение не расходятся.
- Пользователь принимает результат, затем дописывает замечание; ветка вновь открыта. Второй запуск агента получает только открытые запросы.
- Создать конфликт во время ввода сообщения и во время работы агента; проверить сохранность черновика и отказ старого пакета.
- Проверить композицию при ширинах 375, 768, 1280, 1440 px, 200% browser zoom, длинных названиях и кириллице. Панели и фокус не исчезают из доступного интерфейса. Основной сценарий — Chromium, Firefox и WebKit.

Интеграция: typecheck/build frontend, Rust tests/clippy, release-сборка со встроенными обновлёнными ресурсами; реальный Docker Compose smoke и native smoke на Windows в изолированных данных. Проверка Compose включает `just cli comments`, передачу пакета, ответ, render, перезапуск и сохранность. Пользовательский volume не подменяется тестовым. Перед показом обновлённого приложения контейнер/бинарник должен быть пересобран и запущен с новой версией; успешные тесты исходников сами по себе не означают обновления работающего сервера.

Приёмочный сценарий агента: пользователь оставляет замечание «Добавь этап проверки между блоками»; агент через CLI читает запрос, добавляет карточку и связи, отвечает, передаёт на проверку; пользователь видит и принимает результат. Совместимость CLI и инструкции проверяется отдельно с Codex и Claude; если реальный запуск одного из них недоступен, это явно указано в отчёте, без заявления полной живой проверки обоих.

## 13. Следующий этап

После проверки этой письменной спеки пользователь подтверждает её или перечисляет изменения. Затем Superpowers `writing-plans` создаёт отдельный план реализации: миграция/core → API/CLI → renderer/типографика → frontend C/комментарии → документация и полная проверка. План определит конкретные тесты и порядок работ, не меняя контракты этой спеки без явного возврата к дизайну.

Git отсутствует в проекте и остаётся под управлением пользователя. Спека и визуальные основания сохранены обычными файлами; репозиторий для их коммита не создаётся.
