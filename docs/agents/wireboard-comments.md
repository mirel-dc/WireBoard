# Комментарии Wireboard для Codex и Claude

Пользователь оставляет обсуждения прямо на схеме и вручную поручает агенту: «разбери открытые комментарии». Оба агента используют один локальный CLI. Фоновый запуск агента не выполняется.

## Прочитать задачу

Из корня проекта, если запущен Docker Compose:

```sh
just ps
just cli boards
just cli comments BOARD_ID --status open
just cli comments BOARD_ID --status all --thread 1
just cli inspect BOARD_ID
```

Для native запуска замените `just cli` на абсолютный путь к `wireboard.exe`/`wireboard` и добавьте `--data-dir` того же сервера. Не выбирайте случайную доску: используйте название из поручения или уточните неоднозначность. Номер ветки и revision берите из ответа, а не из примера ниже.

`comments` возвращает единый снимок: boardId/title/revision и threads. Ветка содержит историю сообщений, anchor, последний anchorSnapshot, orphaned, живой target, связанные connectors, endpoints связи и ближайший содержащий frame. Если объект удалён, target=null, orphaned=true: снимок объясняет прежний контекст, но не даёт права автоматически воссоздать объект. Если поручение неясно, ответьте уточнением с submitForReview=false.

## Изменить схему и ответить вместе

Создайте UTF-8 файл `operations.json`:

```json
[
  {"op":"update","id":2,"patch":{"title":"Пользователь","text":"Вход через email и пароль"}},
  {"op":"comment_reply","threadId":1,"author":"codex","text":"Добавил описание входа. Проверьте карточку пользователя.","submitForReview":true}
]
```

Для Claude используйте `"author":"claude"`. Не ставьте `author:user` от имени агента. В одном пакете сохраняются все изменения и ответ; не публикуйте «готово» отдельной транзакцией до правки схемы.

```sh
just upload operations.json /data/comment-operations.json
just cli apply BOARD_ID --revision REVISION --file /data/comment-operations.json
just cli comments BOARD_ID --status awaiting_review --thread 1
just cli render BOARD_ID --output /data/review.png
just download /data/review.png review.png
```

Посмотрите изображение и проверьте результат. Пакет атомарен: ошибочная операция отменяет его полностью. `submitForReview` обязательно: true переводит ветку в awaiting_review и записывает revision всего пакета; false оставляет open для вопроса или сообщения о проблеме. Агент не может отвечать в resolved, закрывать или перепривязывать ветки. Пользователь принимает результат или добавляет замечание, которое снова открывает обсуждение. Если проверка выявила проблему уже после ответа, агент может вернуть активную ветку в open новым сообщением с false.

## Конфликты и потерянные ответы

При HTTP 409 снова прочитайте comments и inspect, учтите новое сообщение пользователя и пересоставьте пакет. Не повторяйте старый пакет с подставленной revision без проверки. При потере соединения сначала прочитайте доску: операция могла сохраниться. Сверьте новые сообщения/ID/изменения; не отправляйте ответ второй раз вслепую. При неопределённой записи сервер блокирует дальнейшую работу: перезапустите его и проверьте сохранённый документ.

Не меняйте boards/*.json напрямую и не публикуйте runtime.json/приватную браузерную ссылку. `just upload` используйте только для файлов операций, не для подмены хранилища.

## Создать комментарий

```json
[{"op":"comment_create","author":"user","text":"Проверь этот блок","anchor":{"type":"element","elementId":2,"u":1,"v":0}}]
```

Допустимы привязки element (u/v от 0 до 1), connector (elementId/t от 0 до 1 по длине маршрута), point (x/y в координатах доски). Фрейм использует element. Только пользователь выполняет comment_status с open/resolved и comment_reanchor с новым anchor.

Комментарии входят в JSON и Undo/Redo, сохраняются после перезапуска. SVG/PNG/презентация остаются без комментариев. Дублирование объектов не копирует обсуждения. Лимиты: 500 веток, 100 сообщений в ветке, 10000 сообщений на доске, 4000 символов в сообщении, 100 операций в пакете и 32 MiB JSON.
Контекст `comments` содержит описание встроенного изображения (`imageEmbedded`, `imageMime`), но не его base64-данные. Для визуальной проверки используйте `render`; полный документ доступен через `inspect`.

## Защита команды от повтора

Новые ответы сохраняйте с `apply ... --command-id UUID --actor-id SESSION --author codex` или `--author claude`; author сообщений должен совпадать с source команды. Весь batch изменений и comment_reply сохраняется атомарно. Генерируйте новый UUID для нового batch. При потере ответа выполните `command BOARD_ID UUID`: квитанция означает успешное сохранение. Если её нет, повторите исходные аргументы и неизменённый файл с тем же ID; не заменяйте revision автоматически. CLI хранит исходный запрос в data-dir/requests. После конфликта прочитайте свежий контекст и создайте новую команду с новым ID.

История браузера отменяет только собственные user-команды и сохраняет независимый текст агента. История и квитанции переживают перезапуск, переносимый экспорт их не включает. Статус awaiting_review по-прежнему закрывает только пользователь.
